## 如何拆解每一步的贡献

这里的“性能”分三类：**取证质量、最终回答质量、运行成本/速度**。证据覆盖提升不等于答案正确率提升，单条SQL提速不等于Agent端到端提速。所有差值用**百分点（pp）**，并标明对照条件。以下读取已有结果，不新增API请求。

| 环节 | 已有对照能支持的贡献 | 不能据此声称 |
| --- | --- | --- |
| 解析、来源与Metadata | 原文定位、期间过滤、表头/单位保留、入库一致性 | 没有独立拆除对照，不能报“解析提高X%答案准确率” |
| 切块/表格上下文 | v1同检索设置下，结构512普通context→table-context：dense 83.11%→87.11%；hybrid 74.67%→94.67% R@10 | 两个增幅不能累加；不是41题答案分数 |
| Planner | 聚焦查询在旧20题使最终覆盖67.66%→69.81%；只改善2题、18题持平 | 不能当作“有Planner vs没有Planner”的贡献；最新时间规则只有离线契约验证 |
| 粗排/融合 | 同候选global RRF回放使最终覆盖67.66%→68.77%，但2题退步；BM25替换一路查询另有+3.87pp | RRF的全部收益尚无同条件移除对照；不同实验的差值不能累加 |
| LLM精排与装入context | 同Top80、逐题双输入预算：47.34%→67.66%，17题提高、3题持平，必需证据102→146组 | 没有运行答案生成，不能称答案准确率提升20.32pp |
| Context数量/压缩 | rank10→rank30为+10.75pp，但实际证据量增加；全池选行另有+2.61pp且U12退步 | 不是零成本收益，也不是全题改善 |
| 生成/计算 | 已记录少量同context算术对照及退步；41题有可审核的端到端初评 | 还没有新旧生成策略在同41题上的单变量收益 |
| ANN、LangGraph与控制 | ANN测近邻保留和SQL耗时；LangGraph测状态、路由、预算/取消/失败合同 | 没有证据证明换框架本身提高财务回答分数 |

旧20题最初的漏斗为：候选94.47% → Top80 80.95% → rank30/8K实际context 47.34%。225组必需证据中最终漏123组：16组候选就未找到、33组在窗口外或窗口内span不全、74组在Top80内但最终没选中。最后一类占漏证据的60.2%，这解释了为何先优化精排/context，而非立即换embedding。[漏斗与候选池大小](../reports/public/experiments/funnel.json)。这仍是位置归因；不证明每一处语义错误的唯一根因。

## 切块与早期检索

v1 dev宏Recall@10的部分结果，完整28组见[v1_dev.json](../reports/public/experiments/v1_dev.json)：

| 配置 | dev R@10 |
| --- | ---: |
| recursive384 plain dense |44.0%|
| recursive768 contextual dense |68.7%|
| structure512 contextual dense |62.0%|
| recursive768 contextual hybrid + domain query |87.3%|
| structure512 table-context hybrid + domain query |94.7%|
| 同上 + parent expansion |92.0%|
| Markdown tree domain control |87.1%|

有些行同时改变多个变量，不把差值归因于单一算法。domain_query含当时的显式词汇扩展，不能冒充新Planner自动改写。选中结构/表格配置后，v1冻结test宏R@5/10/20为71.33%/86.00%/100%；@10跨文档子集全证据完整1/5。[冻结原始结果](../reports/test_release.json)。旧test未用于后续v2策略选择。


**解决什么。** 普通文本切块可能把表头、单位、指标行分开；仅检索到数字行不能保证模型知道年份/量纲。当前`make_chunks`按结构与token上限分割，为embedding保留公司/报告FY/章节前缀，给表格补相邻短标题/单位并保留来源span。报告FY前缀用于定位报告，不替代表内事实期间。实现见[ingestion/chunk.py](../src/finrag/ingestion/chunk.py)。

**如何验证贡献。** 上表44.0%→94.7%同时改了切块、查询与检索策略，不能全部归给chunking。更接近单因素的是固定`grouped=true / domain_query=true / parent=false / k / 查询语言`，只换索引表示：

| v1 dev对照 | 普通结构context | 表格context | 差值 |
| --- | ---: | ---: | ---: |
| Dense R@10 | 83.11% | 87.11% | +4.00pp |
| Hybrid R@10 | 74.67% | 94.67% | +20.00pp |

两组说明表格表示与检索方式有交互，不能合成+24pp或宣称普遍提升20pp。索引表示还影响embedding和最终上下文，未单独分离“向量更易命中”与“上下文补全”的份额。结构512与结构900的普通dense配置分别62.0%/47.33%，也反证切块配置不是越大越好。当前保留结构512/64+table-context；没有建立完整XBRL事实/单位类型系统。

**为什么没有默认扩大父段。** 在表格hybrid配置中parent展开94.67%→92.00%；在另一结构配置中却可改善。可能是必要上下文与重复/预算竞争的权衡，单看均分不能锁定唯一原因。保留来源绑定的小表展开，没有不加区分地扩整章。

### 为什么精排有效，具体贡献是什么

粗排回答“语义像不像、多个查询有没有共同命中”，而金融取证还要判断“这个片段是否实际包含某个需求需要的数字、期间或说明”。例如，与问题同主题的风险段不一定能代替收入表；这是机制说明，不是新增实测案例。

当前[rerank.py](../src/finrag/retrieval/rerank.py)让DeepSeek读**原问+明确needs+公司范围+候选原文编号行**，候选内容按每批最多32项/约16K代理tokens拆分（不等于完整HTTP请求token上限）；输出0–4相关性、支持的need ID与行号，校验候选ID/need/行范围。它是LLM打分路径，不是调用embedding服务计算第二遍余弦。

随后[evidence.py:select_reranked](../src/finrag/retrieval/evidence.py)按分数、支持need数量与原粗排顺序选择，去除高度重叠的来源，并检查证据及完整生成输入预算。默认不启用按模型行号压缩，仍保留原表/来源上下文。因此47.34%→67.66%应归于**这条精排评分+下游选择路径**，不是纯粹更换一个排序模型的数学独立效应。它没有增加召回候选，改善的是同一候选池里有限输入预算的分配。

| 同一20题的逐项变化 | 无精排rank30 | Top80 LLM | 变化 |
| --- | ---: | ---: | ---: |
| 最终宏覆盖 | 47.34% | 67.66% | +20.32pp |
| 命中必需组 | 102/225 | 146/225 | +44组 |
| 全证据齐全 | 2/20 | 4/20 | +2题 |
| 平均证据代理tokens | 7,956.75 | 7,823.30 | -1.68% |
| 平均完整生成输入代理tokens | 17,428.15 | 16,526.10 | -5.18% |

17题提高、3题持平。U15从6/18→13/18；但U02只从0/8→2/8，表明精排不能保证找齐所有跨期输入。[逐题记录](../reports/public/experiments/rerank.json)。证据/生成输入没增加，**总成本却增加了精排API**。在后来的41题中，精排花费$0.5956101，占整轮$0.91794642的64.89%；这是该轮费用构成，不是这次旧20题精排消融的新增费用。

### 为什么不直接上全候选或最高均分方案

- Top80→全池保留原表：67.66%→71.45%，多10组、+3.79pp，但完整题仍4/20。旧全池每题29–573候选、平均177.85；Top80窗口实际平均75.3。候选评分工作量约为2.36倍，不能按候选数直接断言API账单也恰好2.36倍。原始输出没有逐臂独立冷运行账单，整轮$0.7652不能当作一个方案的单题成本。
- 全池原表→模型选行：71.45%→74.06%，多4组、+2.61pp；但U12由11/11跌到9/11。切掉必要的会计行/说明会让均分掩盖关键退步。
- 再做模型need均衡：74.06%→75.24%，多2组、+1.18pp，仍只有4题完整，U12没有恢复。模型输出的need支持不是已经核实的覆盖。

因此目前保留有界Top80 LLM、原表来源、8K/24K双上限，而非把最高实验分数设成默认能力。全池可补Top80外的候选，但仍补不了整个召回池里没有的证据。

### Context数量与预算策略为什么不能只看“多给一点”

rank10→rank30提高10.75pp，但实际平均证据量4,326→7,957，约增加84%；两者虽然同为8K上限，**实际消耗不相同**。item cap=30也不等于最终30块，rank30实际平均19.55项。

need-budget30代理策略在相同8K上限下为45.16%，低于rank30的47.34%（-2.19pp）。按需求分配名额是合理方向，但代理相关性/成本评分不代表真正语义支持；错误分配也会挤掉需要的会计表。这个失败实验不支持“按need分就必然更完整”。

## 粗排与聚焦子查询

- [coarse.json](../reports/public/experiments/coarse.json)：8组固定Top80的离线回放，新增API=0。全局RRF最终67.66%→68.77%，但U14/U17退步；候选内BM25不能找回全库未召回证据。
- [focused.json](../reports/public/experiments/focused.json)：不改chunk/index/过滤/查询槽位/每次k，wide/focused/mixed最终67.66%/69.81%/66.78%。聚焦组两题改善、18持平；仅新候选补评分，旧评分复用，未生成答案。
- [funnel.json](../reports/public/experiments/funnel.json)：候选宏94.47%、Top80宏80.95%、rank30/8K宏47.34%。未覆盖123组中的16/33/74分别损失于召回、窗口、窗口内选择；这是阶段归因，不是唯一语义根因证明。


### Planner和子查询的贡献怎样归因

[agent/planner.py](../src/finrag/agent/planner.py)把原问映射为公司、报告/事实期间、needs、至多4个task/每task至多2个dense query；[search.py](../src/finrag/retrieval/search.py)再按公司×报告FY执行取证。作用是避免一个宽查询只找到最显著的一个子问题，也保留排除条件和历史公开截止。这个能力不能用旧`domain_query`词表扩展的成绩代替。

聚焦对照保持chunk/index、范围、SQL槽位、每job k、Top80及context预算不变，只改变取证查询表达：

| wide→focused | wide | focused | 变化 |
| --- | ---: | ---: | ---: |
| 候选覆盖 | 94.47% | 94.07% | -0.41pp |
| Top80覆盖 | 80.95% | 82.24% | +1.29pp |
| 最终覆盖 | 67.66% | 69.81% | +2.15pp |

这不是“找得更多”，更像是让特定输入在前80保留得更好；这是由阶段变化支持的解释，尚不是每题唯一因果证明。只有U02（2/8→5/8）和U15（13/18→14/18）最终改善，其他18题持平。只补新候选评分、复用旧判断，未生成新答案；mixed宽/聚焦混合反而66.78%，不能简单叠加所有改写。

**尚未独立量化。** 原问直检vs当前Planner的同条件raw-query消融尚未完成；规范题已明确实体/期间，不能证明口语、歧义和澄清恢复能力。最新`temporal_scope`把分析期间与`as_of`分开，并说明默认范围/关键澄清；当前只有离线合同验证，不能说已修复41题中3个旧失败或提高了答案分数。

### 粗排融合为什么有用，又为什么可能丢证据

当前不是把所有余弦分数直接排在一起，而是[search.py:rank_records](../src/finrag/retrieval/search.py)按task/company-FY组融合变体排名，再交错组与任务：`score = Σ weight/(60+rank)`。它避免不同查询分数尺度不可比和单公司挤占窗口，但按“组/任务公平”不等于按“必答事实价值最优”。RRF不是只允许dense+关键词；默认仅dense，也会融合多个dense查询的排名。

global RRF固定候选和历史评分回放使Top80 80.95%→82.18%、context 67.66%→68.77%，+1.11pp，但U14/U17退步，所以没有仅按均分替换默认。纯按cosine重排最终66.87%，也未更好。候选内重排只能从池内选，不能修复首次召回缺失。

41题U15.07的年度PPE、fabless、代工等证据在粗排504/190/209名；Top80精排再强也看不到它们。这是已定位的窗口损失，不是证明必须扩大context或更换embedding。[41题公开基线](../reports/public/baseline41.json)中的阶段宏覆盖93.15%→87.97%→78.55%，也提示现在仍须同时检查窗口与context，不能照搬旧实验60.2%的失证据分布。

## 同SQL预算的重组／BM25／专用精排

每组342次SQL、同index、Top20/job、Top80、逐题匹配上下文预算；对照使用exact以隔离检索方案，LLM复用部分历史判断，CrossEncoder在各shortlist上重新评分。不是线上默认HNSW的独立冷请求评测。

| 取证方案 | 精排 | 候选宏 | Top80宏 | 最终宏 | 完整题 |
| --- | --- | ---: | ---: | ---: | ---: |
| 原dense |LLM|94.47%|80.95%|67.66%|4/20|
| 原dense |CrossEncoder|94.47%|80.95%|59.20%|4/20|
| 证据目标重组 |LLM|95.62%|79.19%|67.62%|5/20|
| 证据目标重组 |CrossEncoder|95.62%|79.19%|55.82%|4/20|
| BM25替换第二dense槽位 |LLM|94.77%|83.87%|71.53%|5/20|
| BM25替换第二dense槽位 |CrossEncoder|94.77%|83.87%|58.90%|4/20|

[serving.json](../reports/public/experiments/serving.json)含6组汇总与120条逐题记录。71.53%与focused的69.81%来自不同实验，不串成同一条累加提升曲线。当前默认仍dense+LLM；缺独立holdout与答案支持验收，不宣称BM25或CrossEncoder普遍优劣。


**BM25为什么可能补充dense。** 财报中的明确产品名、术语、义务与表格标题可能更适合词项匹配。对照用BM25替换第二条dense查询槽位，保持342次SQL，候选覆盖只+0.30pp、Top80却+2.92pp、最终+3.87pp，说明收益更多体现在候选排序/组合，而非单纯增加池规模。最终完整题4→5。这仍是旧开发集取证结果，未验证答案质量或独立新公司泛化；当前未默认启用。[retrieval/lexical.py](../src/finrag/retrieval/lexical.py)。

**为什么任务重组没改善均分。** 按共同证据目标跨公司取证，候选95.62%高于94.47%，但Top80降到79.19%，最终67.62%与67.66%近乎持平。重组后的任务/候选竞争、窗口分配或context选择都可能抵消更大的池覆盖；现有汇总不能唯一归因。复杂planner不是天然更好，当前`regroup=false`。

**为什么专用CrossEncoder没有胜出。** 同dense候选/Top80下，LLM 67.66%、CrossEncoder 59.20%，差-8.46pp。但这比较的是两条精排路径，不是纯架构理论比较：当前CE输入原问等JSON与`embedding_text`、输出一个相关性分数；LLM显式读needs、公司范围和源文行，输出多需求支持。因此本结果只能支持本配置下保留LLM，不能推广成所有金融任务LLM优于CrossEncoder。41题64.89%的精排费用仍是未来比较CE/减少批次的理由，不能直接把CE降分换成成本优化成功。[selection.py](../src/finrag/retrieval/selection.py) · [Voyage接口](../src/finrag/providers/voyage.py)。

## ANN与规模条件

真实小库[ann_real.json](../reports/public/experiments/ann_real.json)：59次实际HNSW索引检查，Top20与exact平均重合98.98%。后续扩容用已有向量加噪、归一化、100个合成文档桶，没有新embedding调用。

100k合成数据的代表组，完整99条参数结果见[ann_synthetic.json](../reports/public/experiments/ann_synthetic.json)：

| 过滤后保留比例 | 方法 | 近邻重合 | SQL p95 |
| --- | --- | ---: | ---: |
|100%|exact|100%|450.06ms|
|100%|HNSW M32 /ef1000 /scan20k|99.17%|5.52ms|
|100%|IVF lists100 /probes10|99.58%|18.24ms|
|1%|exact|100%|6.39ms|
|1%|HNSW M32 /ef1000 /scan20k|94.38%|10.94ms|
|1%|IVF lists100 /probes30|96.67%|59.32ms|

环境：PG17.11、pgvector0.8.6、1024维、单客户端、关闭并行、固定24个缓存查询各重复2次，OS缓存未严格控制。M16在此强聚簇分布发生严重漏召回；高分参数是对同合成分布调参得到，不能直接当成真实金融语料参数。采样RSS不是数据库总RAM。大型隔离测试数据已删除，不自动恢复；不以表中SQL毫秒数宣传服务SLA。


**ANN贡献的是检索速度/规模，不是财务语义理解。** 在表中100k、100%保留的合成条件，HNSW该参数SQL p95约比exact低81.5倍，并保留99.17%的exact近邻；1%过滤时，exact只需扫很小的子集，6.39ms反而优于该HNSW的10.94ms。高度过滤查询不能假定ANN总是更快。真实小库exact/ANN平均6.75/6.35ms，差异很小。近邻重合是相对exact的近似检索保留率，不是gold证据Recall，更不是回答准确率。表中高扫描参数也不是当前线上默认ef100的实测成绩。

## 生成、计算和Agent运行层的独立贡献

### 为什么召回更好，答案仍然可能错

[answering/generation.py](../src/finrag/answering/generation.py)按need组织答案、要求来源ID，允许一次结构修复；这能检查有没有section、引用ID是否合法等，**不能自动证明引用支持、期间/单位或会计解释正确**。

41题已观察到：U19.02来源中的billion数值正确，输出“亿美元”时却少十倍；U15.07原文明确是季度，答案仍用于年度比较；U02.04实际context有库存输入，生成却声称缺失。它们不都是换chunk/增加Recall能解决的问题。另一方面U04.02缺收入输入是真实context缺口，生成也不能凭空补齐。严格span Recall还可能漏算等价替代披露，应人工复核而不是随成绩改gold。

历史6题可靠性/算术跟进中，两轮均恢复6/6交付，原对照只有3/6；但4→46/84数值交付包含了恢复交付与算术方案的共同影响，不能全部归给计算工具。更可分辨的相同plan/evidence三题中：U11 0→17/20、U04 3→0/9、U06 1→3/16。输入/公式/符号角色选错时，Decimal正确执行也会输出错误财务结论。算术和实验prompt仍为opt-in，不能报稳定端到端收益。[评分方法与历史跟进](evaluation.md#six-case-reliability-and-arithmetic-follow-up)。

### LangGraph、预算、Trace应该怎么评价

[agent/graph.py](../src/finrag/agent/graph.py)管理节点/条件边，[policy.py](../src/finrag/agent/policy.py)限制次数、费用、deadline/取消，[core/tracing.py](../src/finrag/core/tracing.py)与UI记录状态和位置。它们的已验证贡献是可检查的状态、可控失败与防止无界调用，不是“装上Agent框架提高X%答案分数”。当前没有framework-only语义质量或吞吐A/B。缓存只在输入身份匹配时减少新增调用，不能把换了prompt/plan的旧缓存当作免费命中。

## 还缺哪些消融，才能回答每一步对最终答案贡献多少

| 要验证的主张 | 应固定的上游与对照 | 最终结果与代价 |
| --- | --- | --- |
| Planner能否理解真实提问 | 同一批raw/口语/歧义输入，直接查询vsPlanner；同范围和总SQL上限 | 意图/约束保留、恰当澄清、答案rubric、失败与费用 |
| Rerank能否改善最终回答 | 先固定真实候选及问题，无精排vsTop80 LLM；同context双上限和生成模型 | 证据覆盖与五维/数字/引用分别评分；记录精排新增成本 |
| 更聚焦/BM25是否值得推广 | 分别单独替换一项，保留成功对照及未调过的新意图 | 粗排/最终证据、答案质量、逐题退步；不多给SQL/token名额 |
| Context压缩是否保住必要解释 | 同候选和grade，原表vs压缩，校验标题/单位/期间/会计行 | Context完整性、答案错误、token与额外调用；必须保留U12式反例 |
| 生成/计算契约能否减少实质错 | 固定实际evidence，当前生成vs一个新契约 | 单位、期间、假缺项、数值覆盖、引用支持、修复失败和成本 |
| ANN是否适合真实大库 | exact参照、真实过滤分布/新公司数据、固定资源 | gold证据损失、近邻保留、SQL及端到端p95/RPS、内存 |

每组应报告宏均值、逐题改善/持平/退步、全部失败分母、成本与实验身份；保持同父问题族/变体在同一split。接口/算法单元测试不代替真实模型质量对照。当前41题是新的开发baseline，未对每个模块逐项移除；因此目前只能量化上述已做的局部对照，不能给出每一步对26/41严格通过的贡献百分比，也不能把各实验pp直接相加。本页没有启动这些付费实验。

## 复现、校验和费用

1. 只核验公开汇总的逐题算术与文档链接：`python scripts/verify_public_evidence.py`。不需DB、密钥或私人Notion。
2. 复算保留的公开结果：`python scripts/verify_public_evidence.py`，不依赖原始run。旧driver和大trace已删除；来源hash只标识当时的输入，不能用于恢复已删除材料。
3. 全量重做需要按[数据说明](data-and-ingestion.md)准备语料，gold不入运行时，通过当前`python -m finrag.evaluation`入口创建新run。历史`context_experiment`、`coarse_experiment`、`focus_experiment`、`rerank_experiment`及旧`experiments/`driver已退休；不能直接从新clone一条命令重做所有旧数字，来源hash也不能恢复已删除原始响应。
4. 缓存缺失的embedding/LLM会计费；本次公开整理没有启动新的付费实验，也未重新生成答案。配置、模型版本、数据范围和随机条件变化后应创建新结果，不能覆盖冻结回执。

后续最重要的是未参与调优的新意图holdout、答案数值/引用支持与拒答评估，再做真实扩库、并发和端到端成本。当前没有完整人工候选相关性标签或生产并发RPS/SLO成绩；41题已有串行样本端到端耗时，不能当作生产负载验收。
