# 项目深挖：从财报问题到可核验证据

[项目首页](../README.zh-CN.md) · [实验明细](experiments.md) · [代码地图](development.md#follow-the-current-query-in-code) · [成功／失败案例](examples.md)

## 1. 定位与事实边界

目标用户是在多家公司、多份年报之间比较产品、风险、收入与现金流披露的研究者。核心问题不是让模型总结几百页，而是回答时不漏比较对象、能区分财年与会计口径，并知道缺少什么证据。

当前交付是**有界 RAG 工作流与本地研究界面**：5家公司、16份 SEC HTML 报告、4,961个服务索引 Chunk。问答、跨年／跨公司取证、引用和运行追踪已实现；没有自主 Agent 循环、标准财务事实库、生产计算器、预测或估值服务。不以“用了 LLM”作为已经完成 Agent 的证明。

## 2. 沿两条数据流读代码

| 阶段 | 输入 → 输出 | 代码与约束 |
| --- | --- | --- |
| 采集/入库 | HTML + Filing/Company → 完整发布文档 | `serving/ingestion.py:ingest_html`；相同不可变来源跳过，冲突在付费 embedding 前拒绝 |
| 解析 | HTML → 段落/表格 Blocks | `parse.py`；保留 DOM、规范文本位置、合并单元格网格；不做通用 PDF/OCR |
| 切块/嵌入 | Blocks → Chunks + 向量 | `chunk.py`、`serving/providers.py`；结构目标512/overlap64代理tokens、来源前缀、1024维 Voyage document |
| 原子发布 | 元数据/原文/块/向量/词法统计 → publication | `serving/store.py:publish`；单文档事务，查询只看发布完成的文档 |
| 在线入口 | question/as_of/可选确认范围 → Trace | `serving/api.py` → `runtime.query` → **`runtime.execute`**；不是入库入口 |
| 规划 | 原问 + 可用报告目录 → needs/tasks/queries | `planning.py`；最多16needs/4tasks/每task2queries，校验范围，必要时澄清；不读gold |
| 召回/粗排 | 受限 query×公司/报告 → 候选/Top80 | `planned_retrieval.py`、`serving/store.py:search`；默认HNSW每job Top20、RRF c60、分组/任务交错、保留≤512 |
| 精排 | 原问/needs + 带行号候选 → 相关性分数 | `reranking.py`；默认DeepSeek真实API，0–4等级、need与行范围，分批≤32，缓存复用；不是embedding分数代替精排 |
| 上下文 | 候选/评分/原表 → Evidence | `rerank_context.py`；来源去重、表格扩展、≤30项、8K证据与24K完整输入代理tokens |
| 生成/观察 | Evidence + plan → 分项答案/缺项/引用 | `answering.py`；引用ID与结构校验；`tracing.py`及网页展示实际调用，不展示模型内部思考 |

图、准确配置和数据库表含义见[架构文档](architecture.md)。一个步骤会调用多个文件：`runtime.py`串联阶段；`generation.py`是Planner、LLM精排、答案生成共用的模型与计费适配器。浏览器代码地图显示当前函数与行号，旧Trace没有的源码身份不会被伪造成历史快照。

## 3. 关键选择、替代方案和代价

| 决策 | 为什么这样做 | 代价 / 何时重新评估 |
| --- | --- | --- |
| RAG vs 全文上下文 | 多文档证据、来源/日期过滤、显式预算与可追踪引用适合当前研究目标 | 没有做完整长上下文对照；少量全文可能更省工程。RAG会在召回、排序和裁剪中丢证据 |
| HTML vs PDF/多模态 | SEC HTML直接提供表格和iXBRL容器，能保留原文定位 | 表格网格不等于标准财务事实；图像、扫描件、PDF排版尚不能覆盖 |
| pgvector vs FAISS/独立向量库 | 元数据、原文、向量、词法统计与文档事务共存，减少同步链路 | 数据库运维和过滤后的ANN损失仍需验证；独立向量服务可能适合不同负载，但本项目没有实测选型胜负 |
| 结构切块512 + 表格上下文 | v1开发对照支持该选择，避免标题/单位与表格完全分离 | 第一批表头行和不可分割长行仍有启发式；复杂v2未重新穷举所有切块，不把旧高分当泛化保证 |
| Dense / BM25 / RRF | Dense处理表达差异，词法补精确术语，RRF合并排名而非直接混加不同分数 | BM25不是PostgreSQL `ts_rank_cd`；索引统计需要随入库维护。新BM25路线是替换查询槽位，不无限增加SQL |
| Top80 + LLM精排 | 限定处理量，输出need/原文行判断；可直接利用既有模型API | 可能在Top80前已经漏证据；LLM评分会误判且增加成本/延迟。专用CrossEncoder已测，但此开发集未胜出 |
| Python工作流 vs LangGraph/DeepAgents | 当前调用图有限、重试和预算可显式表达，不必增加状态框架 | 未来有跨工具迭代、恢复/持久状态或委派需求时再做同条件对照；检索函数并不是独立Agent |

模型不是用固定财务词表强行替换原问；公司别名是可维护业务元数据。模型输出仍必须通过范围和预算契约，失败时不静默放宽公司/日期过滤。

## 4. 评测到底量了什么

主要20题来自真实研究问题及补拟跨公司问题，经过参考答案与证据复核；含225个必需证据组和123项数值检查。多组证据需要同时满足，同组允许替代原文。Gold在选择证据之后离线加载；相同意图的口语变体不能随机拆成“新holdout”。

- **候选召回**：合并搜索结果是否含必需原文；**Top80召回**：精排窗口是否仍含原文；**最终上下文召回**：真正给生成模型的文本/来源跨度是否覆盖。
- **宏平均**先算每题覆盖率再平均；**微平均**按证据组计数。20题的需求量不同，两者不相同。
- Recall未覆盖全部相关Chunk标签；因此未标注不等于无关，不能直接得到可信的Precision/MRR/nDCG全套成绩。
- 引用编号存在不等于引用支持结论。123项数值检查用于参考答案的算术/口径审计，尚未作为生产计算工具或全量在线答案评分。
- RAGAS使用Testset/IDBasedContextRecall相关格式与指标；没有声称运行LLM出题/裁判就完成独立验收。

v1的30dev/30test是另一组较简单任务，参考内容最初由GPT离线草拟，仍有人工语义复核局限。v1冻结测试Recall@10=86%，跨文档全证据完整仅1/5；不能用@20的100%证明任意问题可答。[原始冻结回执](../reports/test_release.json)。

## 5. 三个值得深入讲的排查案例

### 候选94.47%，为什么最终只有47.34%？

原20题候选池平均177.85个Chunk，Top80宏覆盖80.95%，无精排rank30/8K最终47.34%。123个未覆盖证据组中，16个未被召回，33个在Top80之外，74个已在窗口内但未入上下文。[逐层诊断摘要](../reports/public/experiments/funnel.json)。

据此先区分召回、粗排、选择器问题，而不是同时换embedding和chunking。把10项上限放宽至30项后，实际平均证据输入从约4.3K增到8K；这不是相同实际成本下的提升。LLM精排后Top80方案达到67.66%；全候选保留原表达到71.45%，但要对更多候选付费和等待。进一步模型选行平均分更高，却使U12丢掉利息费用/净利润行，因此没有只看均分就默认采用压缩。[上下文/精排原始汇总](experiments.md#上下文与精排)。

### 聚焦问题与复杂任务拆解并非必然更好

保持索引、查询槽位、过滤和Top80不变，聚焦子查询将最终覆盖67.66%提升至69.81%，两题改善、其余持平；不是所有阶段都提升。进一步按共同证据目标重组任务，候选覆盖达到95.62%，Top80反而降到79.19%，最终67.62%。同SQL总预算下，BM25替换第二条dense变体达到71.53%，因此保留为候选配置；未用开发分数直接更改默认。[逐题可检查结果](../reports/public/experiments/serving.json)。

### “用了HNSW”不能直接推出规模验收通过

真实2,759块语料的59次带过滤查询，HNSW/exact Top20平均重合98.98%。之后用缓存向量扰动合成10k/30k/100k，零embedding API；强聚簇100k样本暴露M16构图与漏召回问题。单加搜索参数或构建内存并未可靠解决，M32与不同ef的结果也存在明显权衡。

100k合成全库下，一组M32/ef1000达到99.17%近邻重合、SQL p95约5.52ms；1%过滤时exact约6.39ms，反而比该ANN组更快。这些是单客户端、固定24查询×2次、暖机/未控制OS缓存的SQL测量，**不是财报证据Recall、生产端到端p95或RPS**。大型合成数据已删除，保留配方与汇总，不为展示再次占用大内存。[完整参数结果](../reports/public/experiments/ann_synthetic.json)。

## 6. 可靠性、数据权限与错误处理

- `filed_at <= as_of`、公司/报告范围是业务约束，不是租户ACL。当前只有loopback服务，没有公网鉴权/多租户授权承诺。
- 相同原文可幂等跳过，冲突在付费前拒绝；单文档原子发布避免查询半成品。不能保证未来任意解析器均不漏HTML。
- 结构化Planner最多一次定向修复；provider/计费未知不盲重试。空证据或范围不明确有显式状态，生成/精排失败不会冒充成功。
- 共享费用账本先预留再结算，无法确认的请求保留预留，不把未知费用当0；示例费用是保守列表价估算，不是发票。
- 并发准入在工作线程发起付费前执行。浏览器断线不提前释放仍运行的任务；进程重启不是持久任务恢复。
- 有SQL/provider单次超时，但尚无经过负载验收的统一端到端deadline。没有自动数值与引用语义兜底保证。

## 7. 下一步怎样证明改进有效

先保留现有20题为开发数据，用GOOGL/AMZN新增自然问题和新意图建立未参与调优的holdout；再分别测范围保持、证据完整性、数字/单位/期间、引用支持与部分回答。随后做冷/热成本、真实新增文档ANN过滤损失、失败注入和代表性并发负载。财务事实与确定性公式先做小范围收益对照，之后才进入预测/估值，不以增加Agent数量代替数据质量。
